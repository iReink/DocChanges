# Исправления по пользовательской паре Word, версия 0.2.0

Проверены `old_generated.docx`, `new_generated.docx` и исходный `atlas-report.docx`. SHA-256 исходных файлов совпадают с указанными в старом отчёте. Приведённая в переписке внешняя оценка использовалась как список гипотез; выводы ниже проверены по самим файлам и новым результатам программы.

## Что было неверно в старом отчёте

- 34 записи смешивали смысловую единицу и отдельные фрагменты diff. Цена с прописью, длительность с числом/прописью/окончанием и email дробились на несколько записей. При этом повторение одной цены в разных пунктах действительно является отдельными местами изменения и не должно исчезать из отчёта.
- Отображаемый фрагмент отличался от точного: вставка цифры показывалась как вставка всего нового числа без старого значения. Расширение выделяемого слова захватывало соседнее слово у удаления «не». Поэтому нельзя было надёжно интерпретировать подпись операции по напечатанному фрагменту.
- Проценты неустойки не имели категории финансового изменения; срок, записанный только цифрами, мог остаться обычным текстом.
- Email не распознавался правилом реквизитов. Категория «Таблица» указывает расположение и допустима, но не заменяет категорию «Реквизиты».
- Пункт 2.4 пересекает границу страниц. В PDF между частями одного абзаца стоят колонтитулы. Поиск непрерывной строки терял весь абзац, включая замену «обеими Сторонами → Покупателем».
- Единый флаг неполноты смешивал чтение текста и точность координат. Поиск изменений не зависел от успешной привязки каждой строки к PDF.

## Что реализовано

1. Два уровня данных: группа изменения и её точные посимвольные фрагменты. Поля суммы вместе с прописью, срока, процента и email сравниваются целиком. Связанные правки внутри предложения объединяются; два разных поля в одном предложении остаются разными событиями. Группировка основана на правилах, не на предположении о юридическом риске.
2. На этой паре — **20 групп вместо 34**, без потери фрагментов. Все 18 изменённых абзацев/ячеек воспроизведены точно: применение атомарных фрагментов к старому тексту даёт новый текст. Число 20 не задаётся в алгоритме.
3. У «3 % → 30 %» внутри группы находится вставка одного нуля; у «0,03 % → 0,3 %» — удаление одного нуля. Удаление отрицания показывает «не», не соседнее «входят».
4. Привязка пересекающего страницы абзаца допускает только полное монотонное совпадение текста с пропуском межстраничных вставок. Произвольный несовпадающий текст внутри одной страницы не принимается как точное совпадение. Все 20 событий получили доступные координаты нужных сторон.
5. Текстовый результат публикуется до преобразования Word в PDF. Каждая версия получает просмотр независимо. Во время уточнения результат помечен предварительным; выгрузка окончательного отчёта становится доступна после завершения. Интерфейс обновляется без перезагрузки страницы и сохраняет выбранное изменение.
6. Для PDF-просмотра работает прогретый LibreOffice с приватным UNO pipe. Запуск выполняется один раз на сервер, документы открываются скрыто, без выполнения макросов и обновления ссылок. DOC → DOCX использует ранее проверенный CLI-путь. Модели и лимит VRAM не изменены.
7. Контексты для GLiNER дедуплицируются; уже сопоставленные кодом абзацы не отправляются на ненужное семантическое сопоставление. Точные совпадения ограничивают дорогой поиск небольшими изменёнными участками.
8. Отчёты PDF/DOCX — таблицы с повторяющимися заголовками. Обычная строка Word-отчёта не разрывается между страницами; большие фрагменты допускают перенос. Полнота анализа и точность навигации разделены.

## Измерения на этом ПК

После прогрева конвертера, с уже загруженной локальной моделью, один HTTP-прогон дал:

| Наблюдаемое клиентом событие | От отправки запроса |
|---|---:|
| Список 20 групп и тексты условий | 3,5 с |
| Страницы согласованной версии | 8,6 с |
| Страницы полученной версии | 12,8 с |
| Окончательный результат с ИИ | 16,2 с |

Чтение структуры и первый diff внутри обработчика заняли 0,61 с. Остальное включает запуск обработчика, преобразование и чтение геометрии, HTTP и опрос. Сам отдельный прогрев LibreOffice занял около 25 с при запуске; он не повторяется для каждой версии. Холодная модель может увеличить время окончательной классификации, но текстовый результат и подготовка страниц выполняются до неё.

Это измерение конкретной пары и ПК, не гарантия десяти секунд на любом ноутбуке. LibreOffice экспортирует готовый PDF целиком: отдельные страницы незавершённого PDF не выдаются. Ускорено появление целого документа; просмотрщик отображает выбранную страницу по запросу.

Повторный прогон после простоя с тем же работающим конвертером: список — 2,3 с, страницы первой версии — 4,9 с, второй — 7,5 с. Его материалы: `work/user-regression/stable-release/`. В постоянном процессе удерживается пустой скрытый документ и соединение UNO, чтобы закрытие последнего пользовательского документа не завершало конвертер.

## Проверки

- 46 автоматических проверок сравнения, группировки, координат, API, подписей и задач — пройдены. Ещё 2 проверки политики моделей — пройдены.
- Повторно пройдены 9 направленных сочетаний DOC/DOCX/PDF на искусственном наборе: по 5 изменений, добавленная строка считается один раз. Три неизменённые пары дали 0 событий.
- Проверены ранний результат до вызова конвертера, независимая готовность сторон, запрет финального отчёта до завершения, стабильность ID группы после появления координат, разделение ограничений текста и навигации.
- Табличные PDF и DOCX отрисованы и просмотрены. В контрольном Word-отчёте 2 страницы; в PDF — 3. Набор данных для обеих выгрузок общий.
- Материалы измерений: `work/user-regression/final-release/metrics.json`; исходные результаты/координаты и отчёты сохранены рядом. Окончательная проверенная вёрстка отчёта — `work/user-regression/layout-final/`.

Автоматическая проверка разрешений отклонила перезапуск основного работающего сервера без подробной причины. Новые изменения проверялись отдельным экземпляром на порту 8002 с отдельными временными задачами. Для применения новой версии к основному процессу нужно вручную выполнить `stop_all.bat`, затем `start_all.bat`.

Прежние ограничения остаются: OCR отсутствует, сложные PDF требуют контроля полноты; классификация не является юридической оценкой риска. На отдельном старом ноутбуке этот прогон не повторялся.
